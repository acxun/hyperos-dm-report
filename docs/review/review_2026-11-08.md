## P2：证据及技术表述应修正

### 6. “重试返回 200”不能单独证明“无防重放”

- 位置：`docs/executive_summary.md:30`。
- 判断：相同 AES 密文重试只能说明确定性加密/客户端重试；HTTP 200 不能证明服务端重复入库或未做去重。RSA PKCS#1 v1.5 加密的 `sign` 还可能每次不同，相同 body 并不自动等于相同完整请求。
- 建议改为：**“观察到重复密文请求及成功状态码；服务端是否进行重放检测、去重或幂等处理未验证。”** 若要证明重放，需要定义完整请求重放条件及可观测业务副作用。

### 7. 加密风险论证存在已知明文的循环论证，“无法解密”过于绝对

- 位置：`docs/report_public.md:28,163-166,820`；`README.md:115`；`docs/gaps.md:13`。
- 已证实部分：`SystemHelper/g1/c.java:23-26,63-65` 确认 AES-ECB 与原始 16 字节 MD5 密钥；`e1/e.java:42-45` 确认 RSA 包裹密钥而不是数字签名。
- 问题：已经取得某条完整明文后，能解密对应密文不是额外泄漏未知数据的证明；不能据此暗示可解密其他流量。更关键的设计风险是确定性密文、候选明文的离线验证、缺少可见的认证加密机制与 HTTP 暴露。
- “200 包不可解密”“仅凭密文无法解密”也应限定为**本次缺少匹配明文/密钥，未完成恢复**，而不是协议保证不可能恢复。可预测候选、其他本地副本和密钥来源并不由 HTTP 状态码决定。
- 建议另说明：公钥加密不提供客户端身份认证；但服务端是否还检查其他认证条件、本次是否能伪造有效业务记录，未验证。证书 100 年有效期与自签名也不能直接当作 TLS 校验漏洞，因为这里是内置密钥封装证书，而非已证明参与 TLS 验证的证书。

### 11. 抓包工具有可复现缺陷，会影响完整性判断

- 位置：`tools/pcap_tcp.py:43-45,73-85`；`tools/decrypt_match.py:27-39,42-58,94-95`；`tools/README.md:13-14`。
- 四项合成输入已复现：
  1. 完整握手的 SYN 被作为流基准但没有处理其占用的序列号，`ABC` 被重组成 `\x00ABC`（两个脚本均有）。
  2. 缺失片段被静默填零：`ABC` + 三字节缺口 + `XYZ` 被返回为 `ABC\x00\x00\x00XYZ`，未标记 incomplete。
  3. HTTP 声明 Content-Length=16，实际只有 3 字节时，仍返回请求体。
  4. IPv6 地址按单字节冒号分隔，`2001:db8::1` 返回 `20:01:0d:b8:...:01`，无法直接用标准地址匹配。
- 还有独立的解释错误：未命中本地队列时打印“说明这是一条已成功发出的新数据”。未命中也可能是队列淘汰、取证时序不同、抓包截断、重组错误或明文文件不对应，不能推出服务器成功。
- 建议：在修复前明确工具只用于已验证完整的特定样本；加入完整性状态、正确序列号/连接生命周期处理、HTTP 长度校验与标准 IPv6 格式。成功判断必须关联真实响应，而不是根据“未命中队列”反推。
- 影响边界：工具缺陷不自动推翻已做到全密文逐字节匹配的 R 样本；会削弱对“不匹配”“无流量”“无法解密”的解释。
